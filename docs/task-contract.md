# Task contract v1 (pre-implementation review)

All data are synthetic. Three separate SQLite databases share no tables. IDs are positive integers; text comparisons are case-sensitive SQLite binary comparisons. Dates are valid ISO `YYYY-MM-DD` strings, including 2024-12-31, January 2025, 2025-02-01 and later. Amounts and quantities are integers. Column aliases do not matter; column positions/types do. Every result column is non-NULL unless explicitly stated. `integer` means SQLite integer, `text` means string, `real` accepts finite integer/float numeric values with absolute/relative tolerance 1e-9. No other type coercion. Unordered results are **bags**, preserving duplicates; ordered results require exact sequence including tie-breakers. No implicit sorting is imposed on candidates.

Schemas (PK and FK constraints apply; all columns NOT NULL except marked `?`):

- **commerce**: `customers(id INTEGER PK, region TEXT?)`; `orders(id INTEGER PK, customer_id INTEGER FK customers.id, status TEXT in {paid,pending,cancelled}, ordered_on TEXT)`; `lines(id INTEGER PK, order_id INTEGER FK orders.id, sku TEXT in {A,B,C}, quantity INTEGER 1..5, unit_cents INTEGER 0..10000)`. Orders may have zero lines. Revenue is quantity × unit_cents, paid orders only unless otherwise specified.
- **support**: `agents(id INTEGER PK, team TEXT)`; `tickets(id INTEGER PK, agent_id INTEGER? FK agents.id, opened_on TEXT, resolved_on TEXT?, priority INTEGER 0..3)`; `events(id INTEGER PK, ticket_id INTEGER FK tickets.id, kind TEXT in {reply,note}, happened_on TEXT)`. A resolved date is on/after opened date; events occur on/after ticket opening. Unassigned tickets are legitimate; no implicit agent is created. Agents may have no tickets.
- **billing**: `accounts(id INTEGER PK, plan TEXT in {basic,pro}, active INTEGER in {0,1})`; `invoices(id INTEGER PK, account_id INTEGER FK accounts.id, issued_on TEXT, total_cents INTEGER 0..50000)`; `payments(id INTEGER PK, invoice_id INTEGER FK invoices.id, amount_cents INTEGER 1..50000, paid_on TEXT)`. Payments occur on/after invoice issue; multiple payments and overpayment are allowed. Accounts may have no invoices; invoices may have no payments. Outstanding = total minus all payments, can be negative.

Totals: 12 development, 12 assessment; 14 categories. These are authored evaluation tasks, not a sampled public benchmark. Assessment is task-held-out within known schemas, not unseen-schema generalization. An initial simple world may have none of the hard cases. Non-anchor worlds must include zero-line orders, shared teams, NULL region/assignment/resolution, repeated SKUs/events, no-child entities, exact date boundaries, ties, zero/overpayments and empty intermediate groups. Some whole tables are empty in a dedicated world while preserving constraints, to check zero-row vs singleton-zero behavior.

Rejected/clarified ideas before freeze: “best customer” was rejected as ambiguous; C06 pins revenue and ID ties. “fully paid customer” excludes no-invoice accounts in B04 rather than relying on vacuous truth. “first reply” pins date+ID in S04. “January tickets still open” uses start-of-February resolution semantics in S05, not current status. No approximate string matching or locale collation is supported.
