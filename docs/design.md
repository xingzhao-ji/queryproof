# QueryProof design

Status: proposed for independent review before implementation. Authorization: the user requested autonomous substantive portfolio builds; the parent selected this bounded project. Routine design decisions below are the implementer's choices, not claimed user preferences.

## Purpose and evidence

Build a useful text-to-SQL evaluation workbench for SQL evaluation: show how apparent correctness changes when the same SQL is checked on discriminating database worlds. The contribution is task/answer validity, independent oracle checks, measured grader errors, and actionable diagnosis. It is not a novel benchmark, universal equivalence prover, model training, or a general secure SQL service.

Use 24 precise, synthetic tasks across commerce, support, and billing schemas. Twelve development and twelve assessment tasks are fixed before model capture. At least eight semantic categories are represented. Every task declares column types, nullability, multiplicity and order. The natural-language contract in `task-contract.md` is the source specification. Reject ambiguous task ideas in a small decision log rather than silently choosing favorable meanings.

Each schema gets six deterministic worlds: an intentionally simple anchor, one structured edge-case world, three generated worlds using pinned seeds, and an empty world. Worlds preserve primary/foreign keys, enum and amount/date constraints. The generator, row data, schema DDL, task contracts, gold SQL, control labels and grading policy all receive versioned content hashes. Generated worlds are synthetic and deliberately small; they are not independent model samples. Both task splits use the same six-world policy. The five non-anchor worlds are withheld from the prompt-only candidate generator, not secret from the implementation author.

## Approaches considered

1. Exact SQL strings: easy and deterministic, but rejects valid formulations and cannot express execution semantics. Retain only as a measured baseline.
2. One SQLite database: executable and inexpensive, but accepts accidental matches. Retain as a measured baseline using the anchor.
3. Multiple bounded SQLite worlds with independent non-SQL oracle checks: chosen because it can expose spurious matches and preserve counterexamples with no services or downloads. This is an established approach, as in [Zhong et al., 2020](https://aclanthology.org/2020.emnlp-main.29/), not a novel method. Finite coverage remains explicit. A full SMT equivalence checker, commercial benchmark and container service would exceed this scope and do not replace oracle review. Exact-string is intentionally weak; single-world versus multi-world results and separately authored held-out probes are the meaningful calibration comparisons.

## Oracle and labels

The owner writes gold SQL. The independent reviewer first receives only schema, task contracts and world rows, derives expected results with ordinary Python data operations in an independently authored artifact, and records that work before inspecting gold SQL. All 24 tasks × six worlds must agree before measured results receive credit. Disagreements are adjudicated with concrete rows and contract reasons; changes invalidate affected freezes and precede model capture.

A separate 72-candidate grader-validation pool contains one exact gold, one semantically equivalent formulation and one plausible incorrect mutant per task. Exact-gold sanity controls, equivalent positives, semantic negatives, policy-refused safety probes, and actual model outputs have separate denominators; gold SQL is not an independent positive label. Labels are agent-authored then independently reviewed, not human-annotation agreement. Wrong labels require a natural-language violation plus an actual counterexample; equivalent labels require query reasoning and execution across the finite suite, not a universal proof. If a supposed mutant survives all worlds, improve the world or mark the label unresolved before freeze, never score it as a confirmed negative solely by author intent. The reviewer adds a separately authored held-out grader-probe pool after world freeze to check beyond the mistakes these worlds were constructed to expose. Assessment is task-held-out within known schemas, not unseen-schema generalization.

Root captures real prompt-only Codex-agent outputs in a fresh no-history context after task/prompt freeze and before grading. The exact prompt, raw unedited output, extraction rule, capture date and available session/model metadata are preserved separately. The generator may write answers once through apply_patch to a new capture file, but may not read workspace files, run SQL, inspect oracle/worlds or receive grading feedback. Freeze every planned task/prompt-policy response slot. The primary success denominator includes all planned slots: absent/malformed answers, policy refusals, timeouts and crashes all count as non-success. Any executable-only rate is secondary and labeled; incomplete capture coverage never appears fully assessed. Unknown provider IDs, inference time, tokens, pricing and API reproducibility remain unknown. Hand-authored controls never count as generated model errors.

## Execution boundary

Python standard library and SQLite only. One short-lived Python subprocess executes one candidate/world using a disposable copy of a validated database. Open `mode=ro`, set `query_only`, disable trusted schema and extension loading, authorize only SELECT/READ of this task's schema tables, a small named deterministic function allowlist and recursive query actions needed for supported CTEs. Deny PRAGMA, writes, ATTACH, schema access, extension/file functions and non-whitelisted functions. SQLite `execute` admits a single statement; read-only WITH and window functions are supported.

Limits: SQL 16 KiB; input candidates 1 MiB/256 entries; result 1,000 rows, 32 columns, 256 KiB serialized and 16 KiB per cell; SQLite VM budget 200,000 operations; parent wall deadline 2 seconds including prepare/iteration; SQLite length/SQL/expression/compound/select/column limits; child CPU/file-descriptor/file-size limits where supported. Account serialized bytes per row before appending, never accumulate the worst-case cell Cartesian payload. Worker output is bounded and a killed/crashed child is reaped. Every timeout, invalid output, denial or execution error fails, never passes. Source DB hashes are checked around evaluations. Exact typed bags use multiplicity counters. Approximate numeric bags use bounded bipartite perfect matching (maximum 200 rows) rather than greedy approximate matching; B07 has at most two rows. Order comparisons preserve exact sequence.

This is defense in depth for SQL interpreted by trusted local SQLite, not an OS sandbox. The child runs with the user's OS identity; SQLite/Python native-code vulnerabilities are outside the boundary. There is no attacker-supplied Python, database, extension or schema input. No network functions are exposed. Do not download/start a container without discussing with root. On macOS, address-space limits are not a dependable hard memory isolation mechanism; VM/result/SQLite limits and process deadlines are the claimed controls.

## Durable run and workflow

CLI: `tasks`/`task ID` → `freeze` → `import-candidates` → `run` (resume the same directory) → `report`/`inspect` → `compare`. Candidate imports require unique IDs, known task IDs, bounded SQL and explicit provenance (`authored_control` or `agent_capture`); copied raw bytes and canonical parsed candidates are hashed. Invalid inputs fail before publication.

Run directory stores immutable manifest, copied inputs, source policy hashes and append-only results keyed by candidate/world. Each completed result is fsynced and published atomically without replacing an existing result; a run-wide advisory lock excludes concurrent writers. Resume verifies manifest/input/source/world hashes and existing result envelopes before reuse. A crash between computation and publication can repeat that computation, but cannot overwrite or count it twice. Incomplete runs show coverage and cannot appear complete. Tampered or mixed-policy runs are refused.

Reports distinguish model success from grader calibration. For controls, exact/single/multi graders report TP/TN/FP/FN and false accept/reject denominators overall, by task, category and split, keeping exact-gold sanity separate. For model outputs, primary success uses all frozen planned slots, with capture/completion/missing/error counts; no confidence interval pretending worlds are samples. Failure inspection includes SQL, status/reason, task semantics, first discriminating world ID/hash, full small world rows, expected and actual typed results. A local standalone HTML report may make these JSON diagnostics navigable; no server/dashboard is necessary. The separately authored reviewer probe pool is reported independently after implementation freeze, with pre-fix results and versions retained if it exposes an error; it is not silently merged into authored controls.

## Constraints and acceptance

Source and generated outputs stay inside their explicitly selected project/cache paths. Cache in `~/.cache/job-apps-runtime/queryproof` stays below 200 MiB allocated, host free floor 2 GiB. No credentials, API spend, GPU, container/runtime downloads, private applications or external dependencies. Synthetic dates are ordinary fixture values, unrelated to current user eligibility. Runtime/code hashes record exactly what was executed.

Acceptance: all independent oracle cells agree; all controls adjudicated; measured anchor false accepts are caught across all three schemas and several semantic categories; valid equivalents are accepted under declared result semantics; exact baseline visibly rejects equivalents; blind actual model capture retained; hostile SQL/data limits and real crash/resume are demonstrated; a fresh reviewer can execute the entire CLI workflow and inspect a real failure. Negative findings and finite-suite limitations stay in the README and report.
